# Design conversation connection implementation plan

Spec: ../specs/2026-10-09-design-conversation-connection.md

User authorized implementation in this session. Independent owner-contract, editor bridge and frontend modules are delegated with disjoint file ownership; root implements Orchestrator and integrates. Existing Law changes stay in place and are re-read before shared-file edits. No upstream push.

## Contract

Owner GET/POST `/editor/v1/conversation`, bound to project/branch/conversation_id. Editor GET/POST `/api/v1/platform/projects/{id}/conversation` resolves the owner binding. POST accepts message_id, text and optional site context and returns 202; GET restores/polls authoritative state.

Snapshot: conversation_id, revision, status idle|working|failed, messages (id, role, agent, text, at), artifacts (id, owner, title, data, status), error. Project identity is validated server-side. Owner skill contracts expose versioned instructions and tool argument schemas; they are fetched over A2A, never inferred from skill descriptions.

## Tasks

- [x] Owner contracts: add and test conversation-contract skills in Requirement, DesignIntent, Program. Prompts and domain schemas remain owner-local; existing tools perform computations and validation.
- [x] Orchestrator: persistent conversation receipts, duplicate messages, project isolation, failed models, actual owner calls and bounded iterations. Existing A2A caller and versioned publication reused; explicit intent reconfirmation and idempotent Program recovery added.
- [x] Editor bridge: binding/origin/schema/error tests, dedicated adapter/router and route inventory. Law ask path preserved. POST carries the server-only header.
- [x] Frontend: scoped polling/restoration, owner messages/artifacts, selected project and Law context, sequential delivery queue, explicit version-bound confirmation. Selected-clause chat integration preserved.
- [x] Integration: owner/editor tests, frontend type/API guards, live A2A/model checks and browser checks; concurrent Law changes preserved. See execution evidence and limitations below.

## Review focus

No assumed building type or numeric default; no role-based wizard; no keyword fallback when model fails. Don't conflate model proposal with user declaration. Requirements can be captured incomplete without satisfying downstream gates. Task identity and artifact version survive reload. Stale owner writes, duplicate POST, changing projects, interrupted process and model/agent failure must not fabricate success. A2A structured services must actually be invoked, not just impersonated in text.

## Execution ledger

Models cannot author this confirmation. Program changes invalidate intent and expose a reviewable reconfirmation action.
