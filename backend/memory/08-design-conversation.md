# Design conversation connection — 2026-10-09

User explicitly authorized cross-repository implementation after Law review. Design intent: continuous project chat chooses Requirement, DesignIntent or Program from their live owner-authored contracts and current state. Do not introduce role-based questionnaires, fixed building lists, guessed numbers or model-failure keyword routing.

- Editor door: `GET/POST /api/v1/platform/projects/{project_id}/conversation`. ProjectRepository resolves the owner project/branch; browser identities cannot override them. GET restores/polls; POST returns 202.
- Implementation: `schemas/conversation.py`, `adapters/orchestrator_conversation.py`, `modules/platform/routers/conversation.py`. Upstream is `/editor/v1/conversation`; writes require `X-Editor-Client: local` plus configured network token. Response identity, schema and size are validated.
- Before POST, the backend activates registry entries advertising `design-conversation/v1`; GET only reads. `required_for_capabilities` marks the gateway as mandatory; optional owner outages permit ordinary conversation. Only live validated A2A contracts can execute. The registry owns activation membership, not domain routing.
- Payload: conversation_id, message_id, text, optional context (pnu/address/assessment_date/law_run_id), optional confirmation (artifact_id/context_hash). Confirmations are references to server-stored, exact-version intent proposals, never LLM approval.
- Runtime owner code: `agents/OrchestratorAgent/orchestrator/conversation/`. SQLite conversation history shares DesignStore; duplicate message IDs are deduplicated. Requirement deltas bind canonical previous state, actual user quote and revisions; intent checks bind real geometry; Program builds use normal immutable/publication receipts.
- Owner capabilities: Requirement/DesignIntent/Program advertise `*_conversation_contract` instructions and schemas. Program conversation exposes build, not generate, because generate lacks equivalent original-request publication binding. No owner tool result is inferred from prose.
- Interrupted Program calls journal original args/snapshot and can replay their original idempotency key; stale publication is refused. Validated remote CAS heads are retained separately for subsequent builds. Unknown outcomes block new Program writes, not ordinary conversation. Other interrupted turns are marked failed, never blindly replayed.
- Second review: selected Law runs bind project/branch/PNU/date and owner receipt; historical context cannot borrow current artifacts or tool inputs. Initial intake can precede Law but keeps source-run provenance. Cards refresh from actual state; invalid confirmation becomes stale. Conversation and run terminal states commit atomically, including projection failures.
- 2026-10-12: a message that is one address or PNU (the Site role's deterministic claim, `routing/roles/site.locate`) is the editor's own: the door answers 200 `{located}` from `ask.locate_site` without activation or relay, the frontend drops the pending message and opens the map on the parcel (`controller.onLocated`). Only whole-message addresses; a sentence containing one still goes to the owner.
- Frontend: project-scoped conversation selection, polling, sequential local send queue, stored owner turns, artifacts, reconfirmation and site/Law-run context. Existing Law useAsk remains for selected-clause commands. Pending messages not accepted by the server do not survive full page reload.
- Tests: `backend/tests/test_platform_conversation.py`, `test_platform_projects.py`, route/import guards; Orchestrator `tests/test_*conversation*.py`. Browser tests were mocked; actual model/A2A checks used isolated owner state. Details: `docs/superpowers/plans/2026-10-09-design-conversation-connection.md`.

Runtime changes need process replacement; agent-host owns Orchestrator/backend/Program. Requirement and DesignIntent use ops Docker containers. Do not restart Law merely to deploy these changes.
